# Public TLS smoke test

The GitOps tree adds cert-manager v1.21.3 (including its CRDs), a Let's Encrypt
production ClusterIssuer using Gateway API HTTP-01, a Cilium Gateway in the
`edge` namespace and a disposable HTTP echo workload in `hello-world`.

## Address and DNS

- `hello.archaic.work` must resolve publicly to the home's static WAN IPv4
  address. Existing wildcard DNS covers this name.
- `Gateway/edge/public` requests LAN IP **192.168.1.201**, inside the
  existing Cilium `lan-gateways` pool.
- Forward **TCP 80 -> 192.168.1.201:80** and
  **TCP 443 -> 192.168.1.201:443** on the home router. Do not forward
  to a node IP or the Kubernetes API VIP `192.168.1.110`.
- Avoid publishing an AAAA record unless IPv6 routing to this Gateway is also
  working. Ensure external inbound TCP 80 is allowed; HTTP-01 requires it.
- The HTTP listener accepts cert-manager's temporary Exact-match challenge
  route in `edge`; other HTTP paths redirect to HTTPS. The HTTPS listener
  admits HTTPRoutes only from namespaces labelled `gateway-access: public`.
- The router's DHCP scope must continue to exclude `192.168.1.201-220`.

## Installation and verification

The `gateway-api` and `cilium-networking` Applications already establish
Gateway API CRDs, Cilium's GatewayClass, the LB IP pool and L2 policy. They must
be healthy before testing this deployment. No separate Cilium Helm release is
introduced.

The new child Applications can initially reconcile before their dependencies
finish. Check that `cert-manager` is healthy, that the ClusterIssuer is Ready
and that `Gateway/edge/public` is Programmed. If a dependent app initially
fails while CRDs or webhooks are coming up, re-sync it after the prerequisites
are healthy. Do not manually install duplicate charts or commit generated
Secrets.

From a K3s server:

```sh
k3s kubectl -n argocd get applications gateway-api cilium-networking cert-manager public-gateway hello-world
k3s kubectl -n cert-manager rollout status deployment/cert-manager --timeout=300s
k3s kubectl -n cert-manager rollout status deployment/cert-manager-webhook --timeout=300s
k3s kubectl get clusterissuer letsencrypt-production
k3s kubectl -n edge get gateway public
k3s kubectl -n edge get svc -o wide
k3s kubectl -n edge get certificate,order,challenge
k3s kubectl -n hello-world get deployment,service,httproute
```

Expect the Cilium-generated Gateway LoadBalancer Service and Gateway address
to show `192.168.1.201`. From a second machine on the same LAN, confirm the
VIP is reachable before testing over the WAN:

```sh
curl -v --resolve hello.archaic.work:80:192.168.1.201 http://hello.archaic.work/
```

Before certificate issuance succeeds, port 80 should redirect normal paths
to HTTPS. Once Let's Encrypt marks the Certificate Ready, test from an outside
network (e.g. cellular data):

```sh
curl -vI http://hello.archaic.work/
curl -v https://hello.archaic.work/
```

The HTTPS response should contain `hello from hello.archaic.work` with a
valid publicly trusted certificate. No `-k` / `--insecure` is needed.
On a LAN without hairpin NAT, use this command to bypass the router's public
NAT while still validating TLS:

```sh
curl -v --resolve hello.archaic.work:443:192.168.1.201 https://hello.archaic.work/
```

For ACME diagnostics:

```sh
k3s kubectl -n edge describe certificate hello-archaic-work-tls
k3s kubectl -n edge get orders,challenges
k3s kubectl -n edge get httproutes
k3s kubectl -n cert-manager logs deployment/cert-manager --tail=100
```

The production issuer omits the optional ACME email because no monitored
contact address was specified; add one to `apps/cert-manager/clusterissuer.yaml`
if desired. Let's Encrypt production rate limits apply. Make sure the
port-forwarding is in place before repeatedly re-trying issuance.

## Ownership and removal

The cert-manager chart is installed **only** by the Argo `cert-manager`
Application. Its chart CRDs are kept across deletion. The ACME private account
key, Gateway TLS Secret, Certificate, Orders and Challenges are generated by
cert-manager, not stored in Git. Back up the ACME account key and TLS material
if they become operationally important.

The `hello-world` Application opts into pruning and can be removed after the
test. The `public-gateway` and `cert-manager` Applications do not prune by
default, to avoid deleting shared edge and certificate infrastructure when an
entry is removed from Git. Review actual live objects when intentionally
retiring them.
